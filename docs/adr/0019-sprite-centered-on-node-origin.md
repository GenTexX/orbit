# A sprite is centered on its node's origin

A `SpriteComponent` draws its quad centered on the owning Node's origin: the local quad spans `-size/2 .. +size/2`, so the node's translation is the sprite's center, and rotating or scaling the node pivots about that center with the translation untouched. photon's `Sprite` primitive keeps its top-left anchor; helios offsets by half the rotated, scaled size when it builds render instances.

The first editor gizmo pivoted about the center *by compensation*: the model anchored sprites at the top-left, and rotate/scale drags rewrote the translation each frame to hold the center still. Hands-on use showed the confusion that causes - rotating a sprite visibly changes its position value - and the confusion was the model's, not the gizmo's: a node transform naturally pivots about its origin, so the origin should sit where a user thinks the thing is, which is its center (Godot's Sprite2D is centered by default for the same reason). Keeping the top-left anchor as the model default was rejected: it makes `position` mean "corner", which nobody reads it as. A configurable anchor/pivot field on `SpriteComponent` stays open as a later addition, with centered as its default.

This makes every transform edit trivial (nothing compensates, nothing else moves), keeps the inspector's position stable under rotation and scaling, and shrinks the gizmo math to pure per-property drags. Accepted cost: `position` no longer coincides with the drawn top-left corner (placement math that wants a corner adds half the size), and the anchor question is settled by a default rather than a field - until a real use case asks for one.
