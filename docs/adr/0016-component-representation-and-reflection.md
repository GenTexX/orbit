# Components are a closed enum, edited and serialized through one Reflect trait

A `Component` is a variant of a closed enum (`Sprite`, `Camera`, `Script`, ...) attached to a `Node`. Each component's data struct implements a small `Reflect` trait that enumerates its editable fields as named, typed handles, where the type is a closed `Value` enum of what the engine supports (f32, bool, String, Vec2, Color, an asset reference, ...). The inspector, the scene (de)serializer, and Milestone 5's hot-reload all walk that one `Reflect` contract; none of them hard-codes any component's fields.

We rejected trait objects (`Box<dyn Component>` plus a type registry): open extensibility a first-party component set does not need, and it pushes type tags and dynamic downcasting into serialization and reflection - the same inheritance-shaped ceremony ADR 0014 avoided for widgets. We rejected driving the inspector from serde's data model: serde is built for persistence, not for typed, editable, named rows with per-field widgets, and sharing it would couple the on-disk shape to the UI. We rejected a `#[derive(Reflect)]` macro for now: premature machinery while there are only a couple of components; hand-written impls are small, and a macro can subsume them later without changing callers.

This makes ADR 0003's uniform contract concrete in Rust: "enumerate a Node's Components and their fields" becomes one function the whole editor reduces to. Accepted cost: adding a component edits the enum and writes one `Reflect` impl (fine while we own every component), and the `Value` set is closed, so a genuinely new field type is a deliberate addition.
